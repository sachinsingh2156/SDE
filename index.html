Thinking in Systems

We call it an operating system, not an operating program. That difference is the subject of this whole course.

Teacher's noteWhatever an algorithm does for a program, architecture does for a system. If you want to improve a program, work on its algorithm. If you want to improve a system, work on its architecture.

1.2What is software architecture?

The architecture of a system is the set of structures needed to reason about it: software elements, the relations among them, and the properties of both.Standard definition, as used in Software Architecture in Practice (Bass, Clements, Kazman)

Why bother?

Without an architecture you must take the whole source code, compile it, run it and test it to learn how available or maintainable it is. With an architecture diagram you can reason about the system without implementing, compiling or executing it.

It gets complex quickly

Look up the Linux kernel map: user space, memory, storage, networking, device control, each tile a module, connected one-way, two-way, or one direction at a time. Reducing that complexity is the architect's first job.

1.3Architecture versus design

Common trap"Architecture is high-level design and design is low-level design." This is not correct. High-level and low-level thinking exist inside both activities.
Design

What the system must do

ER diagrams, class diagrams, database schema. Closer to the programmer. An ER diagram tells you which entities exist and how they relate.

Good design gives you the functional requirements.

Building analogy: how many classrooms there are and what the building looks like.

Architecture

How well it will do it

Which components, which back end, SQL or NoSQL, who talks to whom, containers or not, how it is deployed.

Good architecture gives you the quality attributes.

Building analogy: how the walls make the room sound-proof and keep extreme weather outside.

Teacher's noteDo not chase the ideal system. Even very large, heavily funded public portals are not perfect at peak load. Our target is the most appropriate architecture for the situation, not a perfect one.

1.4Requirements: functional, constraints, quality attributes

Functional

What the system must do, or users will not adopt it at all. "A user can log in." Boundary-value and black/white-box testing belong here.

Constraint

A fixed boundary you must live inside. "This hall seats 250." "The client cannot spend more than $20 million a year on development, operations and maintenance."

Quality attribute

How well, with a threshold. "Log in securely." "Thousands log in simultaneously." "On sale day, respond within 5–7 seconds."

The "-ilities"
AvailabilityReliabilityPerformanceScalabilitySecurityMaintainabilityModifiabilityExtensibilityFlexibilityFault toleranceReusability

Two products with the same functions (two mobile operating systems, two office suites, two cloud providers) are told apart by their quality attributes. That is what users call "a matter of choice".

Trade-offs are permanent

  • Security vs performance: every extra layer of encryption, authentication, authorization and auditing slows the system. The most secure software tends to be the slowest.
  • Efficiency vs availability: fewer components run faster, but when one fails everything attached to it fails.

Everything you add has a side effect. Architecture is choosing which side effects you can accept.

Measuring availability in "nines"

AvailabilityUnplanned downtime per year
99% (two nines)≈ 3.65 days
99.9% (three)≈ 8.8 hours
99.99% (four)≈ 53 minutes
99.999% (five)≈ 5.3 minutes

Only unexpected downtime counts; announced maintenance does not cost you customers. An ideal system is unreachable, so we design to add nines.

1.5Taming complexity: cohesion and coupling

We reduce complexity by splitting the system into independent units. Two words judge how good the split is.

Inside a component

High cohesion

Everything inside the component belongs together and forms one logical unit. Give each component one responsibility (the single-responsibility idea from SOLID).

Between components

Loose coupling

A component depends as little as possible on others, and only through a common interface. Example: one PaymentGateway interface with several implementations, injected as needed (dependency injection).

Think about it"One responsibility per component: will that not be slow and create too many components?" More components, yes, but each one is simple. And one responsibility does not mean one request at a time: an authentication component can authenticate millions of users concurrently if it is designed to scale.

A monolithic system is the opposite extreme: one big module with high coupling and low cohesion, no separation of concerns, where a fault in any small piece of code can affect everything.

1.6Two tools of the architect: patterns and tactics

Pattern

A packaged, well-known arrangement of elements that delivers a known mix of qualities. You choose the pattern according to the quality you need. Example: MVC for reusability; load balancing for scalability.

Tactic

A single design decision aimed at one quality attribute. Example: keep replicas in sync to raise availability; use version control to make change manageable. Tactics are often built into frameworks and platforms.

Both come with pros and cons, and both can help one quality attribute while hurting another. Patterns let you decide the trade-off and tell you roughly what degree of each quality you will get.

Chapter 1 recap

  • Program → application → system. Algorithms optimise programs; architecture optimises systems.
  • Architecture = elements + relations + properties of both; it lets you reason before you build.
  • Design delivers functional requirements; architecture delivers quality attributes.
  • Requirements = functional + non-functional (constraints + quality attributes).
  • Aim for high cohesion and loose coupling; accept that every choice is a trade-off.
  • Patterns and tactics are the two tools for steering quality attributes.

Check yourself

"Users must be able to log in securely within 2 seconds." Split this into requirement types.

"Log in" is functional. "Securely" and "within 2 seconds" are quality attributes (security, performance), each needing a measurable threshold. A cap such as "must run on the existing two servers" would be a constraint.

Why can you not maximise security and performance together?

Security is achieved by adding work: encryption layers, authentication, authorization checks, audit logs. Each consumes time and resources on every request, so performance falls. The architect chooses the balance the context needs.

Is version control a pattern or a tactic?

A tactic. It does not structure the system; it is one decision that makes change easier to manage. A good pattern leads to a good design; good version control on a bad design does not.

2.1What makes something a pattern?

A pattern is a known solution to a given problem in a particular context.

Known, so discovered

Think of your habits: silencing the alarm every morning is a pattern because it keeps recurring. A pattern already exists in many systems. You can discover a hidden pattern, but you cannot invent one.

The rule of three

The community usually accepts a pattern once the same solution is seen solving the same problem, in a similar context, in three different (heterogeneous) use cases. MapReduce was used many times before someone named and documented it.

Generic, so reusable

A "Hello World" cannot be reused inside a social network. A pattern is reusable because it is generic and exposes parameters you customise to get a concrete solution.

Teacher's note · anti-patternsSome arrangements are known to cause poor performance or security holes; we call them anti-patterns. But context decides: an anti-pattern in one context can be a perfectly good pattern in another.

2.2The catalogue

Layered

Horizontal layers; each uses only the layer directly beneath it

Two rules. (1) A higher layer may use services of a lower layer, never the reverse. (2) It uses only the layer immediately below; no bypassing. On the receiving side data moves upward, but that is passing results up, not using services.

What you gain
  • Separation of concerns: each layer knows where input comes from and where output goes
  • No cyclic dependency: a change in A cannot ripple to B and back to A
  • Internal logic of a layer changes freely; an interface change ripples to one neighbour only
  • Fault containment and easier security: you know exactly who may call you
  • Each layer can sit on its own machine; a bottleneck layer (say a firewall) can be replicated behind a load balancer
  • Predictability: every request crosses every layer, so you can benchmark each layer and plan capacity
  • Layers are reusable across applications (a payment gateway)
What you pay
  • Performance overhead: every request passes through every layer even when it does not need them
  • Bypassing a layer buys speed but brings back complexity and makes performance unpredictable
  • All layers on one machine is still a single point of failure

Use when responsibilities are clearly separable and you want fail-safe, maintainable behaviour. Also seen in: campus security gates, multi-factor authentication, a library issue workflow, neural-network layers.

Teacher's noteA pattern is about how the system is implemented. It promises nothing about your data's privacy or availability. Those are orthogonal concerns with their own patterns.

Broker

An intermediary that connects clients to servers

Why it exists. Server addresses are public, client addresses are not: a client always initiates the connection. Without a broker, every time you add or retire a server you would have to inform thousands of clients whose addresses you do not even know. With a broker, clients remember one address. DNS plays exactly this role.

Stateless vs stateful

A broker, like a real one, does not do the work; it arranges the meeting. In a stateless application every request can go back through the broker. In a stateful session the client then talks directly to its server until the session ends.

Affinity: send the same client to the same server whenever possible, because its data is already cached there.

Dumb broker or smart broker?

A smart broker measures server load and chooses the best server. That means constant monitoring and extra CPU and memory, and the broker itself becomes the bottleneck. For very high scale, keep the broker dumb (round robin, or pick the freest server).

A broker that starts controlling what servers do has turned into master–slave.

Teacher's note · when is extra work worth it?Suppose a search query is sent to three servers and the first reply is used. Should the broker cancel the other two? If each takes a few milliseconds, no: tracking and interrupting them costs more than letting them finish, and they serve as a backup answer. For long, expensive tasks the balance flips and managing duplicates is worth it.
What you gain
  • Clients are independent of server addresses and count
  • Easy scaling, load balancing and failover to another server
  • A single place for access control
What you pay
  • The broker can be a single point of failure or bottleneck
  • Any measurement or "smartness" is computational overhead
  • If strict ordering is required (ticketing, banking), brokers must be smart and scale suffers; a chat service that tolerates out-of-order delivery scales far more easily

Broker vs bus: a bus lets servers talk to each other; a broker does not. Broker vs master–slave: a master controls what the slaves do; a broker only connects.

Model–View–Controller (MVC)

Separate the data model, its presentation and the control logic

Think of Model ≈ the data model, View ≈ what the user sees, Controller ≈ the decision logic. Each can change without touching the others: swap the database engine and the model stays the same; replace the logic inside the controller and the model and view stay the same.

MVC vs three layers

Both give separation of concerns. In MVC the parts interact in both directions: when data changes, the model tells the view to refresh; the view can ask for an extra field. If you force every interaction through the controller, you have built a layered system, not MVC.

Different kinds of access

Controller and view both reach the model, but the controller may modify it while the view only reads. MVC can be built as modules or as services (the model, view and controller can each be a service).

What you gain
  • Reusability: one model serves many views; one controller drives several views
  • Database, logic and UI evolve independently
  • No more database code tightly glued into program logic
What you pay
  • Two-way interaction is harder to implement than a layered stack
  • Often confused with PAC (Presentation–Abstraction–Control); know that they differ

Pipe and Filter

Independent processing steps connected by data pipes

Without pipes, entity E1 must be built to produce exactly what E2 accepts; adding E3 means changing interfaces, and E1–E2 may break. Here every filter only obeys the pipe's standard, and the pipe handles the hand-over. Use it for data-processing applications, batch or transactional, where input is processed stage by stage.

What you gain
  • Filters are reusable and replaceable
  • The workflow reads naturally, like an invoice moving between departments
  • Easy to evolve by adding a transformation; easy to find the buggy stage
  • Works sequentially or concurrently
What you pay
  • A data format must be agreed between communicating filters
  • Parsing and re-formatting at each stage costs time and compute
  • Filters with incompatible formats cannot be combined

Client–Server and Peer-to-Peer

Fixed roles versus interchangeable roles
Common trap"A server is the more powerful machine." No. Take two identical laptops: the one that entertains requests is the server; the one that initiates the connection is the client. A server might only hand out a roll number while the client does all the heavy statistics. The names describe roles, not computing power.

Client–server

Use when data or processing is shared by many users from many places and it is acceptable to keep everyone's data together.

  • Deploy and maintain functionality once; all clients get it
  • Light, low-cost clients; data survives a broken client
  • Server scales independently (replicas + load balancer); standard interface lets both sides evolve
  • Single point of failure; depends on the network
  • Unpredictable performance because client load varies
  • Limited control if the server belongs to another organisation

Peer-to-peer

Use when large files move between users, you want no expensive central server, no central point of failure, or more privacy.

  • No server cost; data goes directly between peers
  • Grows and shrinks organically with the number of peers
  • Peers must be powerful enough to bear the processing
  • If the peer holding a file is offline, you cannot get it
  • Keeping every peer's view of the topology current is expensive; stale information spreads
Teacher's note · pure P2P hardly existsIn file-sharing networks a tracker records which peers are online and what they hold. Until peers learn about each other the system is really client–server; only the transfer itself is P2P. Pure P2P would need static addresses and every peer knowing every other peer; the moment you add a routing table you have added a server. Likewise, a mobile payment that feels person-to-person passes through banks and a national payment switch.

Service-Oriented Architecture (SOA)

Independent service modules that can use one another

Each service module is independent and can use any other service: think of it as the layered pattern with the fixed sequence removed. A service is invoked by a consumer's request, exchanges data (including feedback) one-to-one, and disconnects. Example: a travel portal aggregating train booking, flights, hotels and catering.

ServiceMicroservice

Publish–Subscribe

Publishers and subscribers decoupled by a middle layer

Publishers keep publishing to channels whether or not anyone listens: fire and forget. Subscribers choose channels and cannot modify the content. When new content arrives the middle layer finds the subscribers and notifies them: one publish, many receivers. A pure pub/sub publisher gets no feedback, like a TV channel that only samples its audience. Examples: news aggregators, channel notifications, messaging pipelines.

Not a load balancer

With a load balancer all back ends are identical. Here every publisher offers different content. (You can still put a load balancer inside the layer for the replicas of one very popular publisher.) The layer is central, so it can be a single point of failure.

Pub/sub vs service bus

A bus is passive, like a city bus on a fixed route: every message rides it, anyone may look, and subscribers must keep checking whether something is for them (pull). The pub/sub layer is active: only subscribers receive the content, by notification (push).

Teacher's note · is "push" really push?Your phone's IP address changes as you move between networks, and all communication needs an IP at the network layer. So the server cannot simply reach you. A client on the phone keeps contacting the notification service with its identity; done frequently, this pull feels like push. Holding an open socket per client is the alternative, but sockets bind server resources (a machine has only 216 = 65,536 ports), so plain polling serves many more clients.

2.3One code base, many services: multi-tenancy

Think about itWhat is the real difference between email, a mobile chat app and a discussion forum? Try listing differences, then check each one: acknowledgements, drafts, threads, attachments, groups, encryption, integration, voting... nearly every "difference" exists, or could exist, in all three.

All three exchange messages between identified users (an email ID, a phone number, a username). Functionally they are the same. What differs is architecture and therefore the experience: look and feel, real-time behaviour, reliability, vendor lock-in, available APIs. Whether a message is "legally binding" or "formal" is a policy or perception matter, not a technical one.

Multi-tenancy

One house, rented to several tenants at once, each logically separated so that they cannot interfere. In software: one code base serving different services or customers. Imagine a single modular code base offering email, chat and forum. It can be applied at hardware, middleware, platform and software level.

Why is it not everywhere?

It is the most resource-efficient answer for software-as-a-service, but the design is much more complex. Heavy load on the mail tenant must never slow the chat tenant; a change for one must not break another. Separate products are simply easier to build if you lack that expertise.

  • A pattern is a known solution to a problem in a context; it is discovered after recurring, and documented with a six-part template.
  • Layered: one-way, no bypass. Broker: hide servers, keep it dumb to scale. MVC: three parts, two-way.

Check yourself

Why does the layered pattern forbid a layer from skipping the one below it?

Skipping improves speed for that request but removes the guarantees: dependencies multiply, a change can ripple to several layers, and because different requests now use different numbers of layers, performance is no longer predictable, so capacity planning becomes guesswork.

A ticket-booking site scales worse than a chat app with far more traffic. Is the booking site badly built?

Not necessarily; it is the nature of the application. Booking must respect sequence (seats are allotted in order, after payment confirmation from a third party). A chat app does not guarantee message order, so its broker can stay dumb and scale. Transactional systems cannot scale like non-transactional ones.

You force all model–view communication to go through the controller. What pattern do you now have?

A layered (three-layer) arrangement. MVC is defined by the direct, two-way interaction among all three parts.

Is a blackboard in a classroom the same as publish–subscribe?

It is close: one party writes, many read. But there is no middle layer with channels and selective notification; everyone sees everything, which is nearer to a shared, mostly read-only data space. A good answer states this assumption and compares the two explicitly.

Process view: processes, not threads

One process may be shared by many modules (a single directory-login process used by every campus application). Draw processes and their communication, but not threads: synchronising threads is an algorithmic concern, not an architectural one.

Physical view: real constraints

Many modules can share a machine, or one module can span many machines. Decide by load, compute needs, and whether co-located processes interfere on data, privacy or performance. Do not put a critical module on an unreliable machine. Multi-zone deployment (say two regional data centres) belongs here.

3.2Drawing conventions and method

Use the symbols everyone expects

  • Cylinder ("drum"): database. Never use it for a web server.
  • Cloud: the Internet
  • Rectangle: component or module
  • Rounded box / ellipse: start and end of a flow
  • Diamond: decision
  • Arrows: show direction: one-way or two-way

Method

  1. Pick a use case and write it as a user story, step by step.
  2. With that story in mind, draw the four views.
  3. Add more stories. After each, check every view still satisfies it for scalability, security, maintainability.
  4. A system may have several diagrams per view; scenarios connect them.

Real systems have thousands of stories. For a small project write about 7–10; for a larger one 20–25.

Teacher's noteA lecture-hall building is designed around stories such as "a visitor can find room 308 unaided". That story becomes requirements: stairs, and a numbering convention where the first digit is the floor. Software user stories work the same way.

Chapter 3 recap

  • Logical → functions; Process → run time; Development → building it; Physical → deploying it; Scenarios → tie and test.
  • Logical view covers functional requirements; the other three carry the quality attributes.
  • Standard symbols make diagrams portable across teams and companies.

Check yourself

Which view would show that your database is replicated in two regions?

The physical (deployment) view. The logical view would still show a single "database" module.

Your team is spread over three time zones and two modules depend on each other. Which view captures the plan?

The development view: who owns each module, the dependency between them, when interfaces are agreed, and the order of development and integration.

Cloud computing gives on-demand network access to a shared pool of configurable computing resources that can be provisioned and released rapidly with minimal management effort.After the NIST definition of cloud computing. 4.3Four deployment models

Private

On-premise, in your own data centre, for one organisation (which may have many users). E.g. an institute's academic ERP. You manage the infrastructure.

Public

Open to anyone, run by a specialist provider with far more capacity and expertise than you can build. E.g. institute email hosted by a large provider.

Community

Shared by several organisations with a common interest. E.g. a national education and research network linking institutes; a shared library service.

Hybrid

A combination of the above. Keep sensitive data on the private side and move everything else to public, so that you get privacy and scale.

How to decide
  • Money: owning is a capital investment, like building a house; cloud is renting. Long-term commitment favours owning; short-term or uncertain use favours renting.
  • Team: is IT your organisation's focus, or do you outsource it?
  • Data: critical data that may not sit on shared hardware stays private; the services can still run publicly and call the private side through an API.
  • Geography: a provider can afford availability zones across continents; a single company usually cannot.
  • Latency: a private cloud near you may respond faster.
  • Vendor lock-in: hybrid reduces dependence on one provider.
  • "Which is more secure?" It depends on the context. A public cloud is more exposed to network attacks such as DDoS; a private cloud in one building is more exposed to physical disaster.
Think about itThree service models × four deployment models = 12 combinations. Which would you pick for (a) a mission-critical real-time system, (b) a public streaming service, (c) a booking system with extreme peaks but little privacy concern?

Guidance. (a) Private, usually building your own on IaaS so it is optimised and under your control; but if a PaaS or SaaS exists that was built for exactly this case, prefer it, because it is already debugged. (b) Public or hybrid, for elastic scale. (c) Hybrid with cloud bursting.

Mission-critical means isolated

Some space and defence facilities develop on machines with no Internet at all and forbid even USB drives. The Stuxnet worm showed why: it reached an isolated nuclear facility on removable media and quietly sabotaged the machinery.

Leveraging the cloud: chaos testing

One streaming company runs small programs ("chaos monkeys") that randomly switch off machines and congest traffic in production, while support services recreate VMs and rebalance load. Robustness comes from using cloud features deliberately, not from merely being hosted there.

  • Five characteristics: on-demand self-service, broad network access, resource pooling, rapid elasticity, measured service.
  • IaaS → build from scratch; PaaS → develop; SaaS → use. Control falls and convenience rises along that line.
  • Private, public, community, hybrid; cloud bursting moves peak load from private to public.
  • The cloud gives you features; your application must be written to use them.

5.1The idea: abstract the hardware

A computer has four elements. Virtualization builds an abstract version of each, and once something is abstract we can control it programmatically, at run time.

Compute4 physical cores → virtual CPUs you can assign, limit and audit
Storagememory and disk carved into isolated portions
Networkbandwidth shared and re-divided on the fly
Applicationsoftware packaged apart from the machine

Managing all four together is the job of the virtual machine manager. An analogy: with a digital twin of a person you could control the twin through an interface. An operating system's page size is fixed when the OS is compiled; a virtualized equivalent can be set at run time.

Common trap · two similar namesVirtual memory (operating systems): a specially formatted part of the disk that works with RAM so that a program believes it has more memory. Virtualized memory (this chapter): a portion of real RAM, say 2 GB, allocated to one VM and strictly separated from another VM's 2 GB. The VM cannot even tell whether it is a VM.

5.2Why virtualize, and what it costs

Think about itTwo browser tabs already keep their results apart, and a crashing office program does not stop your media player. So why do we need virtualization for separation?

What you gain

  • Strict limits: without virtualization a memory-hungry program can exceed its share and slow everything else. A VM given 2 GB and four cores can never use more.
  • Heterogeneity: an application needing Linux and another needing Windows share one physical machine.
  • Better utilisation: a bank's transaction module is busy by day, its batch interest module by night; they can share hardware.
  • Privacy and no interference between tenants.

What you pay

  • Overhead. On identical hardware, the machine without virtualization can run more jobs, because nothing is spent on the separation layer.
  • No extra capacity. You can never create more virtual resource than physically exists.

Analogy: a hall holds more people with the chairs removed, but chairs give each person their own space. Put partitions in the hall and several different classes can run at once; the hall's total capacity has not grown.

Worked exampleA host has 8 GB RAM and 8 cores. Can you create two VMs with 4 GB and 4 cores each? Cores: no. The hypervisor (or host OS) needs at least one core for itself, and cores map one-to-one, so it refuses. Memory: it will let you, because RAM is allocated dynamically; but if both VMs reach their maximum, nothing is left for the hypervisor to translate their calls and the machine hangs.

5.4Kinds of virtualization

How a VM works. The hypervisor translates the guest's instructions and system calls into those of the layer beneath, and exposes only the hardware you designated: these four cores, this much RAM, that USB port. Bare-metal is more efficient because there is only one OS-like layer. Dual boot is not virtualization: you use only one operating system at a time.

Full virtualization

Every hardware component is abstracted and used as a software entity. The guest OS runs unmodified and unaware.

Para-virtualization

Special hooks give direct, efficient access to particular hardware. It needs a guest OS that knows about them; an ordinary distribution will not do. This is why a provider's own tuned OS image is cheaper and faster than a generic one.

Hardware-assisted

The CPU itself provides virtualization instructions (the setting you enable in the BIOS for desktop VM software). The hypervisor skips translation and VMs get their own scheduling queues. Faster, but more complex.

Teacher's note · virtual coresA virtual core is mapped to a physical core, and affinity keeps the same mapping for efficiency. Cores are not over-allocated: in the cloud, one virtual core gives you a full physical core while your VM runs, and it is reclaimed when you stop or terminate it. The cores you rent may be on one physical machine or spread over several.

Why is the JVM called a virtual machine?

Not only because Java is portable; many languages have per-platform kits. It earns the name because it behaves like a hypervisor for Java programs:

Sandbox

A sandbox gives separation: the code inside cannot touch resources outside its allocation. Browsers run pages in a sandbox so that a web page cannot make critical system calls and take over your machine.

The same idea, a namespace that defines what an entity may see and touch, recurs in programming-language packages, in the memory given to a process, and, as we see next, in containers.

Check yourself

Scenario A: 8 GB, 8 cores, no virtualization. Scenario B: same hardware, virtualized. Which runs more jobs at the same time?

A, because none of its resources go to the virtualization layer. B wins only when the jobs need different environments (different operating systems) or run at different times and can share hardware safely.

My application needs Linux and yours needs Windows. Can both run as Docker containers on one physical machine?

Not as plain containers: containers share the host's kernel, so their applications must be compatible with one OS. With a hypervisor we can each have a VM with our own guest OS on the same hardware.

What is the difference between an image and a container?

An image is the built, read-only package of the application and its dependencies (like a class). A container is a running instance of that image (like an object); many containers can be started from one image.

6.1File system versus DBMS

Think about itBefore reading: list three things a DBMS can do that a file system cannot. Then test each one against the right-hand column below.
The usual claimBut the file system…
"A DBMS has indexes"…is indexed too; that is how it finds a file's blocks.
"A DBMS has access control"…has permissions per user, group and role, and can encrypt the whole disk.
"A DBMS stores structured data"Not every DBMS does: a document store will happily keep unrelated documents in one collection.
"A DBMS keeps ACID transactions"Only some do. And open–write–close on a file is a transaction of a kind.
"A DBMS can be distributed"…can be distributed too (distributed file systems form clusters).

So what is the real difference? Three facts settle it.

1

A DBMS sits on a file system

Tables are a logical view. Physically, every database writes its data into files, and the file system puts them on the disk. You cannot install a database on a machine with no file system; that is also why database software is built separately for each operating system.

2

The file system is the generic one

Both store data. The file system is a generic database optimised for a very general task. A DBMS is specific: relational engines for related, transactional data; document stores for flexible, sparse, semi-structured data.

3

The dependency is one-way

A file system survives without a DBMS (your first file-handling programs prove it). A DBMS cannot survive without a file system.

6.2A DBMS is a pattern

Before DBMSs existed, every programmer wrote the same code again and again: lay data out in rows and columns, build an index, count rows, find where the next row goes, relate one table to another. Then they debugged and refactored it, again and again, in oil and gas, in automobiles, in customer management.

Teacher's noteSomeone noticed that this logic recurs across domains with the same outcome. That is the definition of a pattern. It was abstracted out, implemented once, optimised and offered as a service. A database is a product of modular architecture, and for this course the DBMS is a pattern: in a project report you justify its pros and cons like any other.
What the pattern gives you

Managing data

You hand over storage and organisation and stop worrying about it.

Scale

Related rows and columns are retrieved efficiently, where a plain file system would crawl.

Heterogeneity

A schema (metadata) declares mixed types and lengths per field, so varied data is still manageable.

Efficiency

Efficient storage plus efficient retrieval (next section).

Persistence

Changes are durable on secondary storage; a relationship once created does not vanish.

Reliability

Well-tested code with predictable behaviour.

Consistency

Data is kept in the form that model promises: relations, documents or columns.

Redundancy control

Avoid duplicates, or replicate deliberately with a replication factor for availability.

Think about itWhy is a DBMS more reliable than code you write on the file system? Not because of ACID (not all have it), nor schemas (some have none), nor passwords (files have them too).

Answer: because it is a pattern. Its code has been tested and debugged many times over, whereas every line you write yourself must be tested, debugged and refactored by you. And you know what to expect from it, including its limits. A document store may not give referential integrity, yet it is reliable because you know that and plan for it. Like a teammate: reliable means you know what they will and will not do. A system that sometimes meets expectations and sometimes does not is the unreliable one.

6.3Where the speed really comes from

Reason 1

Efficient storage structures

Data is stored along with metadata and indexes (primary, secondary and more), so the engine can go straight to what it needs.

Reason 2

Store together what is retrieved together

Disk is read a block at a time. The DBMS makes the file system keep closely related rows or columns in the same block, so one input/output operation answers the query. The file system alone has no notion of rows, columns or meaning; it might scatter three related rows over three blocks.

Try it. In a table with 120 columns, select columns 1 and 100 together: it is slower than selecting neighbours, because the engine did not expect them together. Commercial engines watch your query pattern and reorganise storage. You do the same by hand with a view: a precomputed set of columns stored together and read in one operation.

Teacher's note · nothing is freeCreate an empty database and one empty table, then look at the disk: space is already used, for the schema, column types and lengths, permitted operators and indexes. As rows arrive, indexes on several columns and across tables grow faster than the data itself. A database buys time with space. If you care about space and not time, plain files are fine; they are just slow to search. It is the same time–space trade-off you met in algorithms.

7.1The Entity–Relationship model

For rough understanding you may think "entity = table", but precisely: an entity is a set of attributes (with its associated behaviour) describing a real-world thing. A relationship exists when attributes of two entities are connected by some logic (equality, comparison, dependency), not by a chance similarity.

Relationships have attributes too

  • Cardinality: one-to-one, one-to-many, many-to-many
  • Existence dependency: a placement-portal record can exist only if the student record exists; when the parent goes, the child goes
  • Relationships can be dynamic: present at one time, absent at another

From ER to relations

  • An entity becomes a relation.
  • A many-to-many relationship becomes its own relation (link table). One-to-one is usually folded in as an extra column.
  • Several phone numbers per person: adding phone2, phone3 columns leaves most cells empty. Model phone as a separate relation instead.

7.5Transactions, serializability and locks

Run transactions one after another (a serial schedule) and nothing goes wrong, but it is slow. Run them in parallel and their steps interleave. The database may pass through inconsistent states in between; what matters is the result.

A schedule is serializable if its result is equivalent to that of some serial schedule.Serializability is about correctness and time order (money must not leave before it arrives). It is not about deadlocks.

Conflicting operations

Two operations on the same data item, from different transactions, where at least one is a write: read–write, write–read, write–write. Swap their order and the outcome can change. Two reads never conflict.

Blind write

Writing an item without reading it first. Imagine someone setting your account balance without looking at the current one.

Conflict-serializableView-serializable
RequirementEvery pair of conflicting operations appears in the same order as in a serial scheduleEvery read sees the same value as in a serial schedule (and the final write is the same)

Example: views equal, conflicts not

A: W1(x=10)  W2(x=5)  W3(x=6)  R4(x) → 6
B: W2(x=5)  W1(x=10)  W3(x=6)  R4(x) → 6

The first two are independent blind writes. The reader sees 6 either way, so A and B are view-equivalent. But the write–write order changed, so they are not conflict-equivalent.

Example: the lost update

R1(x)  R2(x)  W2(x)  W1(x)

T1 writes using the value it read before T2's update, so T2's effect is lost. No serial order gives this result. The fix: roll back T1 and restart it so that it reads the updated value. This is why parallel transactions involve many rollbacks.

Locks enforce the order. A shared (read) lock lets others read; an exclusive (write) lock lets no one else in, not even to read. In two-phase locking a transaction first acquires all the locks it needs, does its work, then releases them. Until release, others see the last committed value.

7.6Seven limits of relational databases

A relational DBMS is an excellent solution for transactional data. It is not a good solution for everything.

1 · Complexity

Real schemas, especially in higher normal forms, are full of constraints, foreign keys and layered indexes. Entities grow linearly; complexity grows much faster.

2 · Schema dependence

The schema is defined first and is rigid. A record that does not fit cannot be stored.

3 · Sparseness

Entities sharing only some features force a wide table with many empty cells: the curse of dimensionality again.

4 · Self-descriptiveness

A many-to-many design gives three relations. From the tables alone you cannot tell which two are entities and which is the relationship: that meaning is lost.

5 · Variability

Values outside the declared domain are rejected, and streaming data arriving at a varying rate is not what it is tuned for.

6 · Scalability

Metadata, indexes and views make on-disk size grow much faster than the data, not linearly with it.

7 · Volume

Large volume means several instances, and keeping several replicas of tables in sync is a headache (Chapter 9).

Teacher's note · no free lunchA relational engine provides ACID whether you use it or not, and ACID is expensive. A photo feed or a lecture-video site does not need transactional accuracy; a slightly delayed update is fine. If you are paying for a guarantee you do not need, you are using the wrong tool.

  • Entity = set of attributes; relationship = logical association, with its own attributes; many-to-many becomes its own relation.
  • Projection picks columns; selection filters rows.
  • High dimensions push records to the boundary; indexes lose discriminating power.
  • Serializable = equivalent to a serial schedule. Conflict-serializable is stricter than view-serializable.
  • Relational limits: complexity, rigid schema, sparseness, lost meaning, variability, scalability, volume.

Why are view-serializable-only schedules a problem for a bank but tolerable for a social feed?

View serializability lets independent (blind) writes be reordered as long as readers see the same values. A bank's writes depend on earlier values and their order, so it needs the conflicting operations in strict order. A feed can tolerate reordered or late posts.

8.1The philosophy

The relational philosophy says everything in the world can be expressed as relations, with the schema fixed before any data arrives. Not everything fits. Real entities are similar in some features and different in others, so we need models that are flexible.

Complement, not replace

Let NoSQL do what SQL cannot. But do not try to rebuild ACID transactions on top of a NoSQL system: you would have to add all the metadata, auditing and logging again, and it would become SQL and lose what made it useful.

Use both

Many real solutions use SQL in one part and NoSQL in another. Each family below optimises one kind of query and gives up something else. None is good at everything.

8.2Graph databases

A graph is a set of vertices V and edges E, where each edge joins two vertices of V. A graph database is inspired by this, but note: it need not be stored as a graph data structure (underneath, adjacency lists and matrices are just arrays and linked lists). What defines it is what it optimises.

The key difference from relational

A relational DBMS stores an entity and a relationship in the same form, a relation, and is entity-oriented. A graph database treats the relationship as a first-class thing with its own meaning and properties: direction, single or multiple paths, first or latest connection, strength, even probability.

Built for transitive queries

Friends of friends, mutual connections, number of hops, shortest or alternative paths. Try it: design a relational schema that answers "count our common friends" efficiently. You will not find a clean one; that query is why graph databases exist.

Use for social networks and geographic or road data (multiple roads between cities make it a multigraph; one-way streets make direction matter). Do not use for transaction-heavy work: traversal is the strength here, and transactional guarantees are not what it is optimised for.

8.3XML: the semi-structured store

XML is a markup language, so why list it under databases? Because it gives a standard way to structure, store and search data. You define your own tags; the tags give enough structure for a query engine to walk the document instead of reading it byte by byte like plain text. More structured than a text file, less constrained than a relation: semi-structured. (JSON is its close cousin.)

The pieces

  • XML document: the data, as a tree from a root element down
  • DTD / XML Schema: which tags are allowed and how they nest
  • Parser: turns the document into a tree to navigate
  • XPath: select by path from root to element
  • XQuery: richer queries with FLWOR expressions (For, Let, Where, Order by, Return), comparable to select–from–where but less powerful than SQL
  • XSLT: transforms and styles documents

Limits

  • Only defined tags may be used, but richer constraints such as "values in this field must be unique" cannot be enforced.
  • Locking works on a node or a path, not on a single variable. Locking a node normally locks its whole sub-tree; the parent stays free.
  • Sub-tree and path searches are expensive tree operations.

Where it shines: as the intermediate format when moving data from one database to another.

8.4Key–value stores and MapReduce

The model

Data is stored as key → value. The key is unique and uniform (a roll number); the value can be anything, in any shape: one person's profile lists work experience, another's does not. That is why it is schema-less. The natural structure is a hash table.

Good and bad at

Fast: fetch the value for a key. Slow: search by value, since you must visit every pair.

Ideal case: phone number → caller name. Also caching. The moment you want to analyse who calls whom and when, it is no longer a pure key–value job.

Distributed key–value data. With millions of pairs spread over many nodes, keys are stored in arrival order, not sorted. Think of an exam hall: seating by roll number means everyone searches for a seat; seating in order of arrival is quick. So writes are fast and single look-ups are slow. That suits write-heavy data that is read in bulk for analysis, such as logs: you never want one log line, you want the pattern.

Common trap"Reduce" does not always reduce the number of keys. Three sentences (three keys) became four words here; ten sentences could become hundreds of words. Reduce means aggregate.
Teacher's noteBoth relational and key–value stores accept many writes. The difference is in the reads: transactional reads → relational wins; analytical reads over write-heavy data → key–value with MapReduce wins. Any model can be converted into any other. The question is never "can it be converted?" but "is it efficient for my queries?".

8.5Document stores

A document is a collection of related key–value pairs (typically JSON) describing one entity completely. That is closer to the real world than a relational design, where one student is split across several tables and must be reassembled with joins.

Use a document store when the application revolves around one entity at a time: user profiles, a product catalogue, recommendations from your own history. Use relational when you retrieve sets of entities by attribute.

Think about itHow is a document in a document store different from a file in a file system? Both have names, both hold data, both are encoded on disk.

Answer: the content of a document is indexed, so you can jump to the right document and field instead of scanning word by word, and it is created, read, updated and deleted through a uniform web-style interface.

Cookies carry information across visits. That is how a nominally stateless search becomes a personalised "bubble", and why accepting only essential cookies matters.

8.6Column stores

Take a relational table and transpose how it is laid out on disk: store each column contiguously instead of each row.

Why it helps
  • Projection-heavy queries: read only the columns you need. Columns always used together can be stored together, even on the same disk in a distributed system, saving slow input/output.
  • Homogeneity: one column, one type, often fixed length. That means arrays and fast random access ("jump to the 20th value"), where a row of mixed types needs linked structures.
  • Better buffer and memory management for the same reason.
  • Compression: column values repeat (ages lie between 0 and 120 across lakhs of rows), so they compress well, e.g. with run-length encoding.
  • Adding a column is cheap: it is simply stored somewhere new. In a row store every record must be shifted or given a pointer to elsewhere.
What it costs
  • Inserting one new record touches every column.
  • Reading one complete entity means rebuilding the tuple from many columns.

Why buffers exist at all

A buffer sits between two parties working at different speeds. The CPU produces results faster than the disk can store them, so results wait in a buffer and are arranged properly later, in a batch. A database cursor is one: the engine runs the query once, parks 100 results, and you fetch them one by one.

Analogy: the chair in a hostel room where laundry waits until you have time to arrange the cupboard.

Compression and information

A 1-terabyte file containing only the letter a carries almost no information; store "a, repeated to 1 TB" in a few bytes. How far data can be compressed is set by its entropy (Shannon): orderly data compresses well, highly random data hardly at all.

Lossless: the original can be rebuilt exactly (identify students by roll number). Lossy: some is gone for good (identify them by date of birth).

Check yourself

An app shows a user's own profile page millions of times a day and rarely compares users. Which store?

A document store: the whole profile is one document fetched in one read, with a flexible schema. A relational design would need joins on every page view. If the app only ever mapped an ID to one opaque blob, key–value would also do.

Why is adding a column expensive in a row store but cheap in a column store?

Rows are stored one after another, so a new field means shifting every subsequent record or adding a pointer from each record to another location, hurting writes or reads. In a column store each column lives separately, so the new one is simply written in a new place.

Audit logs are written every second and analysed weekly for fraud patterns. Which approach?

A distributed key–value store processed with MapReduce: unsorted appends make writes fast, nobody needs a single entry, and the analysis reads everything in bulk.

Distributed Databases

On one machine life is simple: no consistency worry, no connectivity worry. It also cannot scale, and a disk lasts only a few years. This chapter is the foundation for everything that follows.

By the end of this chapter you can

  • Describe horizontal and vertical partitioning

  • Reason about replicas that disagree

9.1Replication and distribution are different things

Replication

Keeps copies. Purpose: durability and availability. If one disk dies, another has everything. The cost: every change must reach every replica.

Distribution

Divides one database across machines. One query may have to visit several machines. Purpose: scale and specialisation.

The two are orthogonal: use either alone, or both together (for instance, pairs of disks that share the data between them, replicated across pairs).

Common trap"We need a distributed database for fault tolerance." That is replication's job. Pure distribution gives only a limited flavour of it: if the machine holding academic records fails, you can still run queries on the demographic part, with fewer features.

RAID (Redundant Array of Inexpensive Disks) keeps redundant copies across an array of cheap disks, but it behaves as a single unit: the program has no idea where its data lies. In a distributed database, developers know the data is distributed and write programs accordingly.

9.2Why distribute?

Good reasons

  • Horizontal scaling when vertical scaling is not enough: billions of queries on one copy is a bottleneck
  • Load balancing and flexible scalability: add or remove nodes on demand
  • Heterogeneous data: keep the SQL-shaped part, the NoSQL-shaped part and large binary objects (images, video) on machines each tuned for that kind
  • Heterogeneous nodes from different vendors behind one symmetric configuration layer
  • Decentralised control: no bottleneck for storage or computation
  • Not wanting to rely on a central agency (as in blockchains, at a price)

The price

  • No linear speed-up. Three shards taking 3 s each will not answer in 3 s: merging the results is still to be done. Adding resources never improves performance in proportion (Amdahl's law).
  • Management overhead of roughly 20–40%, more for highly scalable systems.
  • Uneven nodes: some have SSDs, some old disks. You wait for the slowest, and cannot easily tell a slow node from a dead or compromised one.
  • Consistency: even the best sync takes a fraction of a millisecond, and a read can land inside that window.
Think about it · where should the computation happen?Bring the data to the computation, or take the computation to the data? A stored procedure runs inside the database, like editing shared slides online, instead of downloading the file, editing and sending it back. Either choice, or meeting half-way, is possible, and each combination brings new challenges.

9.3When replicas disagree

In a purely horizontal system all nodes are peers: no leader, no master. That raises two classic problems of distributed systems, leader election and consensus: how do nodes that can only talk to a few neighbours at a time (multicast, never broadcast) agree on a value?

The answer from class: 5, or nothing

Not 7, even though it is newer and the reader saw it twice. At some point all five replicas agreed on 5. The 7 is work in progress: if the transaction fails, it will be rolled back. A value is not durable until every replica has it.

How locking enforces this

With two-phase locking, A must first obtain an exclusive lock on x at all replicas. If the split happens before that, no one is updated and x stays 5 everywhere. If it happens after A and B are updated, x is still locked: a reader either waits or is given the last committed value, 5.

Teacher's noteReplicas never accept a reader's word that another replica holds a different value: the reader is outside the system and might be an attacker. They confirm among themselves. How many replicas? At least three, to survive one failure (with two, you cannot tell which survivor is right). Five to survive two at once.

9.4Distribution transparency

You never tell a social network "fetch my profile from the third replica in that data centre". The middle layer knows where everything is; the user and the application behave as if there were one database.

Access

You see only what you may see, and get no hint that other data sits beside yours on the same disk.

Location

You do not know which machine, data centre or region holds your data.

Replication

You do not know how many replicas exist or which one answered.

Migration

Data moves from a failing disk to a new one, and you never notice.

Failure

Failures are masked, so that functionality continues.

Teacher's note · disks fail every dayData centres use inexpensive commodity disks that last a few years. With millions of disks, simple probability says hundreds or thousands fail daily. A failed disk is swapped, and the new one rebuilds its content from the other replicas. Monitoring may even copy data off a disk that has merely become slow (predictive maintenance). Old mail or files that open slowly are probably coming from a rarely used cold replica rather than a hot one.

9.5Kinds of failure

Chapter 9 recap

  • Replication = copies (availability). Distribution = division by rows or columns (scale). They are orthogonal.
  • Distribute for horizontal scale, heterogeneous data and decentralised control; expect overhead and non-linear speed-up.
  • When replicas disagree, trust the last value everyone agreed on; exclusive locks keep readers away from half-done updates.
  • Transparency: access, location, replication, migration, failure.
  • Failures: hardware, link, message, network partition.

Check yourself

You split a table's rows over three machines with no copies. What have you gained and what have you not?

Gained: horizontal scale and load spread (horizontal partitioning). Not gained: fault tolerance. If one machine dies, a third of the rows are gone until it returns. For that you need replication on top.

Why three replicas rather than two?

With two, when they differ or one fails you cannot tell whether the surviving copy is good. With three, a majority (two) settles it, so one failure is tolerated.

Consistency & the CAP Theorem

Every system design is driven by one question: how consistent must the data be, to what degree, and for whom?

By the end of this chapter you can

  • Explain strong, weak, eventual and causal consistency
  • Explain five client-centric guarantees
  • State the CAP theorem precisely
  • Argue why all three cannot be 100%

10.1What consistency means here

With one copy, consistency only asks "did the write succeed?". With three or five replicas we want all of them in sync, so that data stays correct and reliable across nodes. The chosen consistency model then dictates how you handle concurrency, synchronisation and failures.

Data-centric

Look from the data's side

All replicas should hold equivalent data. If it holds for one client, it holds for all clients.

Client-centric

Look from one client's side

The store may be inconsistent overall, yet appear consistent to each individual client. Different clients may get different levels. "Selfish consistency."

More replicas raise availability and make strong consistency harder. Fewer replicas make strong consistency easier and lower availability.

Implementing strong consistency

Replicas kept in sync, or a primary replica that takes the write and updates the secondaries (the primary is then a single point of failure, and a standby primary must itself be kept in sync). A reader is kept away from a half-done write by an exclusive lock on every replica.

10.4The CAP theorem

A distributed system cannot provide Consistency, Availability and Partition tolerance all at 100% at the same time. At most two can be fully achieved together.Proposed by Eric Brewer (2000) and later formalised by Gilbert and Lynch (2002). In class we reason about it through examples.

C

Consistency

Exactly the same replica everywhere. Even a 0.5 ms delay while syncing is a moment of inconsistency. 100% means no delay at all.

A

Availability

The system responds. To raise it, remove single points of failure: keep at least two replicas.

P

Partition tolerance

The system keeps working as expected even when part of it cannot reach the rest. If you must trim features or quality during a split, you are only partly tolerant.

Common traps1. None of the three is a yes/no switch. Each is a degree from 0 to 100%: strong, causal, eventual and weak are degrees of consistency; an ERP can be fully available at night and nearly down during registration; dropping fancy features during a split is partial tolerance.
2. CAP applies only to distributed systems. A monolith has one copy and nothing to partition; the question does not arise.
Reasoning it out
Startone copy, x = 5. Consistent, but if it goes down nothing is available.
→
Add replicas for availabilitytwo, three, five copies. More availability, more syncing work.
→
The network splitsthe copies can no longer sync
→
Now choosekeep answering and let copies diverge (lose C), or stop answering until healed (lose A). To keep both C and A, you must assume no partition (no P).

A single-site relational engine is the classic CA system: the moment you replicate it you must give up some consistency or some availability, because it was not built to tolerate partitions. Systems that prefer correct answers and reject requests during a split are called CP; those that always answer, possibly with stale data, are AP.

Teacher's noteDeciding which copy is right by timestamp is not a free solution either: the clocks of distributed nodes are not perfectly synchronised, and a timestamp is itself data that must be synced. Self-study: how latency enters this trade-off when there is no partition (see the PACELC formulation), and vector or Lamport clocks.
Exam tipIf you claim "100% consistency" for a project, expect to be asked about nanosecond-level delays. State the degree you provide and why it suits the application: a ticketing system cares greatly about consistency; a social network much less. Then say what you gave up.

Chapter 10 recap

  • Data-centric: strong (one-copy behaviour, costly), causal, eventual, weak (fast, possibly stale).
  • Client-centric: read-your-writes, monotonic reads, writes-follow-reads, monotonic writes, consistent prefix.
  • CAP: C, A and P are degrees; all three cannot be 100% together; it concerns distributed systems only.
  • CA = single-site relational; CP = correct or silent; AP = always answers, maybe stale.

Check yourself

You post a comment and see it immediately, but your friend sees it a minute later. Which guarantees are in play?

Read-your-writes for you (client-centric), over a store that is only eventually consistent for everyone else (data-centric).

A system has five replicas and a partition leaves two on one side and three on the other. What are the options?

It is an application-level call. Favour consistency: serve only where a majority can be confirmed, or refuse writes until the split heals, losing availability. Favour availability: both sides keep answering and may diverge, to be reconciled later. Many systems choose per operation, for example allow reads but not writes.

Why is strong consistency "generally incompatible with availability"?

During every update, the item is unavailable until all replicas acknowledge; and if a partition prevents acknowledgement, the item stays unavailable. Adding replicas for availability makes this waiting longer and likelier.

11.1Processing versus analytics

Data processing

Rearranging raw data into the form you need: formatting, cleaning, sanitising, normalising, replicating and keeping replicas consistent. Processing by itself gives no meaning; it makes later queries and algorithms faster or possible. Example: a messaging pipeline that organises data into topics.

Data analytics

Getting information and meaning out of the data: statistical analysis, generative analysis, visualisation and infographics. Visualisation is part of analytics, not all of it. Example: a web-analytics dashboard.

11.2The Internet of Things as a data source

All the objects must agree on a communication protocol and a data-exchange format, just as a class agrees on one meeting tool and one language. Version or format mismatches are why two devices sometimes cannot talk.

Why IoT matters to a data engineerIndustry analysts put it this way: IoT produces unprecedented volume, velocity and variety of data, and that forces organisations to re-architect their data and analytics capabilities, adopt new data-management technologies and platforms, and create new data-governance policies. That sentence is the reason there is so much work for you.

Re-architect

Data is no longer static. Readings must be stored, processed and analysed as they arrive; for a mission-critical system such as an aircraft, in real time.

New platforms

A spreadsheet was a fine exploration tool once. At this size it is not, hence messaging pipelines, distributed processing engines and analytics dashboards.

New governance

Things are used by individuals, so the data is personal. Live traffic maps come from many people's location data. Explicit cookie consent on websites, required under Europe's General Data Protection Regulation, is one result.

Benefits. External: better personalised services, well-being monitoring, new revenue ideas, more engagement. Internal: closer monitoring, optimised asset allocation, security and stability, lower operating and maintenance cost through predictive analysis, conservation of resources.

11.3What is "big" in Big Data?

Think about it"Big Data means terabytes" or "petabytes". In the mid-2000s a home computer had about 128 MB of RAM, and a 1 GB file was Big Data for it. In ten years a terabyte will be ordinary. A technical definition should be true last decade and next decade. So what is it?

Data is Big Data when commodity hardware cannot handle it without a special arrangement.Commodity hardware = general-purpose machines widely available in the market (a laptop-class machine), not special server-class equipment.

The definition moves with time: as commodity hardware improves, the bar rises. Data centres prefer commodity machines because special hardware needs rare, expensive skills to run, is hard to replace, and may be discontinued by its vendor.

The five Vs

Size alone is not enough. You will meet three-V, five-V and seven-V versions; do not argue about the count. The point is that Big Data needs several characteristics together, or the problem is not hard. Test each one by removing it:

A 50-terabyte archive of identical daily backups is rarely read. Is it a Big Data problem?

Mostly not. It has volume, but little veracity (highly repetitive, so it compresses and deduplicates well), no velocity, little variety, and limited value. It is a storage task, not a hard processing problem.

Is normalising a database "processing" or "analytics"?

Processing. After normalisation the data carries no new meaning; it is just arranged so that certain queries will be answered faster and more safely.

Designing Data-Intensive Systems

What makes Hadoop, Spark, Kafka or a deep-learning framework able to handle Big Data? The same handful of architectural ideas, combined differently.

12.1Three tests for a data-intensive system

1

It handles Big Data

It manages, processes and analyses data with the characteristics of Chapter 11.

2

It processes in parallel

The algorithm divides a task into sub-tasks, runs them together and aggregates the results.

3

It is distributed

The architecture spreads the work over several physical machines.

Common trapParallel and distributed are not the same. A microservice system is distributed, and we do not call it a parallel system. And a single mainframe or supercomputer that handles terabytes is, by definition, not a data-intensive system. All three tests must pass.

12.2Six features the design must have

Scalability

In every direction: up and down, vertical and horizontal.

Fault tolerance

Faults will happen. You cannot avoid them, as you cannot avoid exams; you need the ability to manage them.

Availability

Both momentary and long-term (recall CAP).

Heterogeneity

Nodes from different vendors with different configurations (8 GB here, 16 GB there). No vendor lock-in.

Load balancing

No node overloaded or idle. With unequal nodes this is hard: estimating what a workload needs is like predicting future page references. A dedicated master node usually does it.

Modularity

A fault may disturb one module, never the working of the whole system.

Think about itOne machine has a capacity of 100 units. Your workload is a fixed 85–90 units; it will not grow. Would you run it on one machine or two?

Answer: two. Not for spare capacity, but because of hardware. At a sustained 85%, the CPU heats up, cooling draws more power, and heat slows the memory bus, the disk and the cache. The extra 10% is spent on managing and compensating for that, so 85% utilisation delivers about what 70–75% does. Treat 70–75% as the optimal level, which is why auto-scaling rules trigger around 75–80%.

Why master–worker and not peer-to-peer?

In pure P2P every node must keep exchanging its view with every other node, as routers exchange tables, and the time and space cost explodes. A master, using metadata, can see which worker is slow and move its task elsewhere.

The parameter server

In deep-learning frameworks, workers each train on part of the data or part of the computation graph, and parameter servers hold and aggregate the results. Change the parameters and the same workers compute something different, so several models can be trained at once.

Data parallelism

The data is partitioned; every worker runs the same model on its share; results are aggregated. Use it when the data can be split.

Model parallelism

The model (the computation) is partitioned; each part runs in parallel and the parts are combined. Use it when the data cannot be split but the computation can. Hybrids exist, with harder aggregation.

12.4Fault-tolerance tactics

A failure is not necessarily a system failure: it may be momentary or partial. The tactics below can be combined; some are alternatives to each other.

TacticIdeaOptions and trade-off
RedundancyKeep replicas of data (and standby nodes)Hot standby (running, instant) vs cold standby (archived, slower to wake)
MigrationMove work or data off a failing nodeStop-and-copy: simple, with a pause; fine for a social feed. Live migration: no pause, more overhead and complexity; needed for mission-critical systems such as air-traffic control.
Failure maskingHide a failure by using another node's answerSend the same request to several servers and use the first response; nobody notices the one that failed
RecoveryReturn to a consistent state and continueCheckpoint and restart; rollback (undo/redo); error-detecting and correcting codes (cyclic redundancy checks, Hamming codes). Repair or replace hardware that fails repeatedly.
Sandboxed job agentsRun each sub-task as an agent in a sandboxIf an agent fails, its control block moves to another node and it carries on
Teacher's noteRecovery is not only about data. In this course it also means recovering a processing or analytics task that failed half-way. Since intermediate results are data too, saving them is the principle behind everything in the next two sections.

Checkpointing. Periodically save the state of a running task, so that after a failure it restarts from the last checkpoint and not from the beginning. You know this idea already: the operating system saves a process's control block when it swaps the process out, and a database COMMIT is a checkpoint, the last consistent state.

12.5Case study: Hadoop

Hadoop ingests and stores very large data in a replicated, highly available way on commodity machines and processes it efficiently (a common industrial use is log and service-request processing).

Data failure vs task failure

Data nodes both store and compute. A job is divided into tasks given to different nodes. Replicas already protect the data; the master's concern is tasks. If one node is at 40% while the rest are at 90%, the master gives the same task to another node holding a replica of that block, without stopping the slow one (stopping costs more), and uses whichever finishes first. Tasks are not duplicated up front, only when a lag appears.

What it is good and bad at

Good: read-intensive processing of large, stored data. With three replicas of a block, three tasks can even read it in parallel.

Bad: frequent updates (every replica must be locked and brought to the same state before the data is usable again) and real-time streams.

Compare · a message broker cluster (Kafka)There too each partition of data has replicas, but they are not equal: one broker is the leader and the others are followers, and requests go to the leader. In Hadoop every replica of a block is equivalent and a task may be given to any of them. The purposes differ as well: one manages message queues for publishers and subscribers, the other processes stored data. They work side by side in one pipeline, not as substitutes.

12.6Case study: Spark and the RDD

Spark grew out of a PhD thesis. Its central idea is intuitive, yet it lets Spark run many workloads far faster than disk-based Hadoop processing, by computing in memory.

RDD — Resilient Distributed Dataset: an in-memory data structure holding (intermediate) results, partitioned across the cluster, and able to survive failures.

Teacher's noteImagine a seven-layer neural network that crashes at layer four. The output of layer four means nothing to the user, but if it was saved you restart from layer four and not from layer one. An RDD does this in a distributed setting: if part of an intermediate result is lost, that part can be reconstructed without redoing everything.

The trade-off: memory for speed

Keeping intermediate results costs space, so you say explicitly which ones to keep. Spark needs much more RAM and is faster; disk-based Hadoop processing is slower and needs less. Time against space again.

Where it fits

Data that is added continuously (streaming) suits Spark. Data whose existing values are updated over and over suits neither Spark nor Hadoop; look elsewhere.

Exam tip"How would you use an RDD, or a similar concept, in this scenario?" is a natural question. A good answer says which intermediate results are worth keeping, what failure they protect against, and what the extra memory costs.

12.7The tool landscape and open problems

Two families of tools

Data processing: distributed storage and processing engines and messaging systems (Hadoop, Spark, Kafka…). They give no inference by themselves.

Data analytics: machine-learning and deep-learning frameworks and analysis workbenches (TensorFlow, RapidMiner…).

Each earns the label "data-intensive" by implementing the ideas of this chapter.

Still open (thesis-sized problems)

  • Data retention: must we keep terabytes of raw data for ever, or can we keep the information in compressed form? Some inferences cannot be reversed.
  • Event-stream ingestion: no scalable system yet ingests billions of sensors and processes them in real time, a reason IoT has spread slowly.
  • New substrates: what would a processing system designed for blockchain-style ledgers look like?

Chapter 12 recap

  • Data-intensive = Big Data + parallel processing + distributed architecture.
  • Six features: scalability, fault tolerance, availability, heterogeneity, load balancing, modularity.
  • Prefer horizontal scaling on commodity machines and master–worker control; run at about 70–75% utilisation.
  • Data parallelism splits data; model parallelism splits the computation.
  • Fault tolerance: redundancy, migration, masking, recovery, checkpointing.
  • Hadoop: replicated blocks, slow tasks re-run elsewhere; read-intensive. Spark: in-memory RDDs with lineage; faster, hungrier for RAM.

Check yourself

With four data nodes and replication factor 3, node 4 is slow on its task for block X. What does the master do?

It assigns the same task to another node that already holds a replica of X (node 1 or 2), leaves node 4 running, and takes the result from whichever finishes first. Because the input block and the computation are the same, both produce the same result.

Why is a live sensor feed with in-place corrections a poor fit for Hadoop?

An update must lock and change every replica of the affected block and bring them all to the same state before the block can be processed again. Hadoop is designed for reading and processing large stored data, not for continuous updates or real-time arrival.

How does lineage save work?

Nothing is computed when an RDD is defined; only the derivation is recorded. When an action asks for a result, only the RDDs on its path are computed, and intermediate results shared by several jobs are computed once and reused. After a failure, only the lost part is recomputed from its lineage.
